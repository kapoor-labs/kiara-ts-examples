3 isolated runs per dataset and engine, 1000 ms budget per query per run, 2026-11-01T16:23:59.263Z.
Local working-tree module (not a released package): `C:\Users\anujkapoor\repos\Kiara-ts\dist\index.js`.

## Method

- Same deterministic datasets, conditions, normalization, missing-value and range semantics as the Fuse.js benchmark.
- Native TypeScript runs on Node's JavaScript runtime after type stripping; Array.filter scans every row on every query.
  It uses the shared reference predicate, then slice for limits, materializes requested projections, and returns IDs.
  No index, result caching, or early exit. This is a generic schema-aware predicate, not hand-specialized code per query.
- Exact filters only. Query interpretation is unsupported: Array.filter is not a query parser.
  Fuzzy search, stemming, dictionary correction and completion are not compared.
- Every supported result must have the correct count, unique matching IDs, and exact source order; any failure exits nonzero.
- Three warmup queries; 5–200 measured iterations within the per-query budget (at least five even if over budget).
  Reported p50/p95 are medians of per-run percentiles. Timing includes filtering, limiting, projection and ID materialization.
- Build and forced-GC retained heap are separate from query latency; dataset generation is excluded.
  KiaraDB uses the existing full build, including keyword/trie/interpreter preparation where configured,
  although only exact queries are timed. Native build only initializes the schema-aware matcher.
- Ratios are native p50 / KiaraDB p50: above 1 means KiaraDB is faster; below 1 means native is faster.
  Aggregate ratios are geometric means across shared scenarios. These are one-machine measurements, not universal claims.
